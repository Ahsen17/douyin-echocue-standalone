## 1. 执行摘要

Echocue 是面向抖音直播间出镜人员的实时 AI 互动建议工具。它从真实直播间弹幕流中识别与主播/团队人设有关、正面且有互动价值的内容，过滤高风险、隐私和侮辱谩骂内容，并在目标弹幕发出后尽快生成符合预设人设的短回复建议与提词，通过 Windows 置顶浮窗展示给主播。

MVP 验证的是一个单直播间、人工使用建议且全链路可审计回放的完整闭环，而非自动发言、机构管理或运营分析平台。MVP 采用 Windows standalone client：弹幕接入、处理、生成、人设配置、审计记录和浮窗展示均集成于 client，不建设独立后端服务。甲方预期从目标弹幕发出到浮窗出现建议，端到端时延应尽力控制在 3 秒以内。

## 2. 问题与产品价值

### 2.1 目标问题

主播在长时间直播中需要持续输出。面对与自身/团队人设有关，或能带动氛围的有趣弹幕时，主播容易出现：

- 无法在恰当时机发现值得接的话题；
- 高频互动下组织语言卡顿或回复滞后；
- 长时间直播后话术、口径和人设表达不一致；
- 因负面、侮辱或涉及个人信息的弹幕干扰正常互动。

### 2.2 产品价值主张

在不替代主播发言的前提下，Echocue 为主播提供实时、贴合人设、可快速扫读的互动建议，帮助其更稳定地延续有价值的话题与直播氛围。

## 3. 用户、角色与使用对象

### 3.1 MVP 用户

| 角色 | 定义 | MVP 权限/职责 |
| --- | --- | --- |
| 出镜人员（主播或团队成员） | 实际观看浮窗、决定是否采用建议的人 | 使用 Windows client 与浮窗；系统不代其发言 |
| 直播间配置人员 | 为单个直播间录入并维护人设信息的人 | 配置直播间与人设；具体交互形态待产品设计确定 |

一个直播间的出镜主体可以是单个主播，也可以是一个团队整体。MVP 的直接服务对象始终是直播间出镜人员。

### 3.2 后续用户（不纳入 MVP）

MCN/机构管理员可管理多个直播间、成员、AI 服务和安全规则。这是产品演进方向，不应反向增加 MVP 的账号、组织或多租户复杂度。

## 4. MVP 目标与成功标准

### 4.1 目标

完成真实抖音直播间的可运行端到端链路：

```text
真实抖音直播弹幕
  → 实时接入与规范化
  → 高风险/隐私/侮辱内容过滤
  → 语义分类与候选筛选
  → 基于人设生成短回复建议和提词
  → Windows client 置顶浮窗展示窗口（默认 10 秒）
  → 展示窗口结束后，从最新弹幕重新筛选
```

### 4.2 MVP 成功标准（已确认）

1. 服务通路可完整执行：真实直播间弹幕能够被接入、处理并在浮窗展示建议。
2. 能优先选出围绕主播/团队人设，或有趣、正面、能够带动直播氛围的目标弹幕。
3. 高风险、侮辱谩骂及涉及主播个人信息的弹幕不会进入回复建议生成与展示。
4. 输出包含一条短回复建议和用于组织语言的提词，并与预设主播/团队人设一致。
5. 从目标弹幕发出到建议自动展示在浮窗，目标端到端时延为 **P95 不高于 3 秒**；具体测量边界需在技术设计阶段确认。

## 5. MVP 范围

### 5.1 必须交付（Must have）

| 编号 | 能力 | 说明 |
| --- | --- | --- |
| M-01 | 真实抖音弹幕接入 | 接入一个实际开播直播间的实时弹幕流。MVP 不使用官方 API/SDK，拟调研以 `jwwsjlm/douyinLive` 为代表的第三方开源方案；必须验证其合规性、稳定性、维护状态和实际可用性。 |
| M-02 | 实时弹幕处理 | 对弹幕完成标准化、去重/节流、基础过滤和候选筛选。 |
| M-03 | 风险与隐私过滤 | 高风险、侮辱谩骂、消极攻击及主播个人信息相关内容不进入生成链路；支持通过自然语言描述或关键词维护直播团队专属禁忌。 |
| M-04 | 人设配置与路由 | 支持一个直播团体的多份自然语言 Markdown 人设文档，由甲方或其指定人员维护；不要求用户填写 JSON 或强制结构化字段。支持指定主要出镜人员及其他成员，并按弹幕指向路由到相应人设。 |
| M-05 | 话题识别与筛选 | 优先识别人设相关、有意思、正面、可带动氛围的弹幕。 |
| M-06 | 回复建议生成 | 基于选中弹幕与人设，生成短、可扫读、可由主播自行决定采用的回复建议。 |
| M-07 | 提词生成 | 生成辅助主播延展表达的短提词。 |
| M-08 | Windows standalone client 与浮窗 | 弹幕接入、处理、生成、人设配置与浮窗均集成于 Windows client；浮窗始终置顶。新建议生成后进入默认 10 秒、可配置的展示窗口；窗口结束后隐藏。支持点击穿透、拖拽位置、透明度、字体大小、深浅主题和窗口尺寸调整。 |
| M-09 | 实时控制与基础运行可观测性 | 展示窗口内不生成下一条建议；窗口结束后不补发旧建议，而是基于最新弹幕窗口重新筛选。应能定位弹幕是否接入、是否被过滤、是否生成成功、是否送达浮窗及端到端时延。 |

### 5.2 明确不在 MVP 范围（Out of scope）

- 自动代表主播发送弹幕、评论或私信；
- 多直播间管理、MCN/机构、成员和复杂权限体系；
- MVP 独立后端服务、Web 管理端及其登录/账号体系；
- 聚合型直播互动数据分析、运营报表；
- 移动端、macOS 和浏览器端浮窗；
- 跨直播间的审计中心、协作审核工作台或云端审计服务；
- 复杂的人工审核工作台；
- 非抖音平台接入。

## 6. 核心业务流程

1. 甲方或其指定人员在 Windows client 中为一个直播团体创建或更新多份 Markdown 人设文档，并指定一名主要出镜人员。
2. 出镜人员在 Windows client 中选择目标直播间与本场适用的团队人设配置，并启动助手。
3. 系统连接真实抖音直播间，持续接收实时弹幕。
4. 系统先过滤高风险、攻击性、个人信息及其他定义的敏感类别弹幕。
5. 系统从剩余弹幕的最新滚动窗口中识别人设相关、有趣、正面、可带动氛围的候选内容。
6. 系统先判断候选弹幕是否明确提及、且可识别为某位其他成员；若是，则使用该成员人设；否则使用主要出镜人员人设。
7. 系统选择最适合本轮互动的一条候选弹幕，结合已路由的人设生成短回复建议和提词。
8. Windows 浮窗自动出现并置顶，独占默认 10 秒（可配置）的展示窗口。
9. 展示窗口内，系统不生成下一条建议，也不建立待展示回复队列。
10. 展示窗口结束后，浮窗隐藏；系统丢弃已失去时效性的历史候选，并只从最新滚动弹幕窗口重新筛选下一条建议。
11. 主播自行决定是否、如何将建议用于真实直播互动；系统不自动发送。

## 7. 初步业务规则

### 7.1 优先内容

- 围绕主播或团队人设、状态、行为与既有表达风格的话题；
- 正面夸赞、轻松玩笑、可自然接话的内容；
- 能引出下一句内容或带动现场气氛的话题。

### 7.2 过滤内容

- 明显侮辱、谩骂、攻击、挑衅或恶意消极内容；
- 涉及主播个人敏感信息、联系方式、住址、身份信息或疑似人肉的信息；
- 政治、色情、违法、医疗/金融建议、竞品及交易价格相关内容；
- 甲方或直播团队明确列出的其他禁忌内容。

处理原则：被过滤的弹幕应当被忽略，不触发生成，也不在主播浮窗中呈现。

团队专属禁忌必须可在 client 内单独配置，配置方式同时支持：

- 以自然语言描述不应触碰的话题、表达或边界；
- 以关键词列表补充需要直接过滤的词语或称呼。

### 7.3 团播人设路由

1. 每个直播团体必须指定一名主要出镜人员，其人设为默认且最高优先级人设。
2. 弹幕未明确提及某个可识别的其他成员时，系统一律按主要出镜人员人设生成建议。
3. 弹幕明确提及某一其他成员，且系统能够可靠识别该成员时，系统使用该成员的人设生成建议。
4. 若成员指向存在歧义、置信度不足或没有对应人设，回退到主要出镜人员人设；不得猜测或随机切换人设。
5. 人设内容以 Markdown 自然语言维护；产品应提供可选模板、编辑、预览和生效状态，而不要求甲方填写 JSON 或固定字段表单。

### 7.4 人工控制边界

- 系统仅提供建议，不自动发言。
- 主播可忽略、修改或自行组织表达。
- 每次浮窗仅展示一条建议，不保留最近建议列表，也不提供手动唤回。

### 7.5 实时性与展示窗口规则

1. 系统生成一条建议后，立即在浮窗展示，并开始默认 10 秒、可配置的展示窗口。
2. 展示窗口内不启动新的回复建议生成，也不缓存待展示的生成结果。
3. 展示窗口结束后，浮窗隐藏；此前未被选中或已过期的弹幕不能按原到达顺序继续生成、展示。
4. 系统恢复处理时，只查看最新的滚动弹幕窗口，重新筛选当前仍具时效性的最高优先级候选。
5. 因此，系统以“最新且最值得回复”为优先，而不是以“按弹幕先后逐条回复”为原则。

## 8. 非功能需求

| 类别 | MVP 要求 |
| --- | --- |
| 时延 | 端到端 P95 ≤ 3 秒是持续优化的业务目标；从弹幕到达接入服务开始，至 client 完成浮窗展示结束。未达目标不阻断开发，但不得作为最终可接受状态。 |
| 实时性 | 应持续处理开播期间的实时弹幕，不以轮询抓取替代实时事件流。 |
| 可用性 | 直播期间发生单条生成失败时不能使 client 崩溃；应保留本地排障信息。AI 服务仅由用户手动启动，未开播、下播或用户停止时立即关闭弹幕 WS，不自动恢复。 |
| 一致性 | 生成内容应受当前人设配置约束，避免明显违反其定位、风格与禁忌。 |
| 安全 | 高风险、隐私、侮辱谩骂、政治、色情、违法、医疗/金融建议、竞品及交易价格相关弹幕必须在生成前过滤；API Key 和会话凭证不得进入日志、审计库或导出内容。审计原文属于受加密保护的本机数据，不得混入遥测。 |
| 客户端体验 | Windows 浮窗始终置顶；收到新建议即自动进入展示窗口，默认展示 10 秒后隐藏；展示窗口内不生成下一条建议，且不补发过期建议。 |
| 可观测性与审计 | 记录并可回放每条弹幕的接入、规则、人设路由、检索、生成、展示和终止状态，以及每一步的原文输入/输出与时间戳；Prometheus/OTel 仅记录匿名运行指标。 |

## 9. 关键风险与待调研事项

| 编号 | 风险/问题 | 影响 | 下一步 |
| --- | --- | --- | --- |
| R-01 | 抖音真实直播弹幕的合法、稳定、可持续接入路径尚未确认。MVP 已限定不使用官方 API/SDK，而拟依赖 `jwwsjlm/douyinLive` 等第三方开源服务。 | 无法接入或方案不可持续，即无法达成 MVP 核心闭环。 | 作为技术调研最高优先级，验证仓库维护状态、协议依赖、账号/风控风险、许可、稳定性、时延与可替代路径；未经确认不承诺具体实现。 |
| R-02 | 3 秒端到端时延对弹幕接入、筛选、模型调用和客户端推送均有约束。 | 技术架构、模型和降级策略均受影响。 | 建立时延预算与压测方案，优先选择低时延生成路径。 |
| R-03 | “高风险”“个人信息”“有意思”“人设相关”的判定标准尚不够可测试。 | 直接影响误杀、漏放和模型效果。 | 在产品设计阶段定义分类法、标注样例、规则边界和验收集。 |
| R-04 | 多份 Markdown 人设配置的组织、选择与生效边界尚未定义。 | 可能导致团队场景下生成风格不稳定或用错人设。 | 设计 Markdown 文档模板、配置集合、适用对象/优先级、启动时选择和质量检查机制，同时不将用户输入限制为 JSON 或硬字段表单。 |
| R-05 | 浮窗展示密度、点击穿透与主播操作方式尚未确定。 | 影响直播中可读性与干扰程度。 | 在交互设计阶段产出原型及可验证默认值；展示时长已确认为默认 10 秒且可配置。 |

## 11. 下一阶段：产品设计的输入与待确认项

本轮需求与产品设计输入已完成。进入详细设计前，乙方需要落实以下实现细节，并在 POC 中验证：
